# Формат содержимого

Каждая подтема — один Markdown-файл с YAML-метаданными. Сборщик проверяет файл и превращает его в HTML и данные для вопросов. Ошибка в формате останавливает сборку.

## Расположение

```
content/<язык>/<стек>/<технология>/<тема>/<подтема>.md
content/ru/dotnet/csharp/type-system/boxing.md
```

Каждая папка — раздел, её название и место задаёт `_section.yml`. Без него сборка падает:

```yaml
title: Система типов
order: 1
```

Имена папок и файлов становятся адресом страницы (`/dotnet/csharp/type-system/boxing`), поэтому пишутся строчными латинскими словами через дефис. Темы раздела идут по `order`, затем — темы вложенных разделов.

## Метаданные

```yaml
---
id: csharp.types.boxing        # уникален на весь сайт, не меняется после публикации
title: Boxing и unboxing
level: junior                  # junior | middle | senior: для какого уровня тема; темы выше уровня читателя помечаются
tracks: [backend, fullstack]   # backend | frontend | fullstack
minutes: 20                    # оценка времени, вес темы в прогрессе
order: 3
requires: [csharp.types.value-reference, csharp.oop.interfaces]  # темы, которые нужно знать до этой
quickCheck: [boxing-copy, boxing-where, unboxing-runtime]       # «Я это знаю»: 3–4 вопроса
testMinutes: 6                 # необязательно: время на тест по теме; без него тест без таймера
testSize: 8                    # необязательно: вопросов в одной попытке теста, по умолчанию 8
---
```

В `quickCheck` 3–4 вопроса уровня самой темы, которые проверяются автоматически и за секунды: `choice`, `multi`, `input`, `output`, `fill`, `find-bug`, `parsons`.

## Предварительные знания

Вопросы и задания проверяют только то, что объяснено в самой теме или в темах из `requires`. Если для объяснения нужно понятие из более поздней темы, его называют одной фразой («такая ошибка называется `InvalidCastException`»), но не спрашивают о нём.

Сборщик проверяет, что темы из `requires` стоят в программе раньше — так цикл невозможен. Тема из `requires`, которая ещё не написана, даёт предупреждение, а не ошибку: содержимое пишется постепенно.

## Код

Код в статье — обычный блок Markdown с языком: ` ```csharp ` или ` ```sql `. Сборщик раскрашивает его заранее, в цветах Visual Studio: C# — через Roslyn, поэтому класс, структура, метод и локальная переменная различаются цветом. Сниппет на C# разбирается как файл с top-level statements и стандартными `using` (`System`, `System.Linq`, `System.Collections.Generic`, `System.Threading.Tasks` и другие), их не нужно писать. Ещё подсвечиваются ` ```xml ` (файлы `.csproj`) и ` ```shell ` (команды в терминале: программа, ключи, строки, комментарии `#`). Блоки на других языках, например ` ```text `, показываются без подсветки.

Комментарии в конце строк стоят рядом с кодом: два пробела после самой длинной строки группы. Группа — строки подряд без пустой строки между ними; в ней комментарии выровнены в один столбец.

```csharp
int a = (int)o;         // ок
long c = (long)(int)o;  // ок: распаковали int, потом сделали long
```

## Рисунки

Рисунок — SVG-файл рядом со статьёй:

```markdown
![Описание для экранного диктора](boxing-memory.svg "Подпись под рисунком")
```

Сборщик встраивает SVG прямо в страницу, поэтому цвета рисунка следуют теме сайта. В SVG цвета задаются только через переменные с запасным значением для светлой темы: `fill: var(--fig-panel, #F3F2F7)`. Доступные переменные: `--fig-panel`, `--fig-cell`, `--fig-line`, `--fig-text`, `--fig-muted`, `--fig-accent`, `--fig-accent-soft`, `--fig-ok`, `--fig-ok-soft`, `--fig-err`, `--fig-err-soft`. Обязательны `<title>` и `<desc>` с описанием рисунка словами.

Классы и `id` действуют только внутри рисунка: сборщик добавляет к ним имя файла, поэтому `.big` в двух рисунках на одной странице не конфликтуют. У корневого `<svg>` не должно быть `class` и `id`, а в `<style>` — только простые правила, без `@media` и других `@`-правил.

Рисунок нужен везде, где речь о памяти, порядке выполнения, потоках данных или устройстве структуры: это объясняется картинкой быстрее, чем текстом.

## Структура урока

Урок делится на шаги. Каждый шаг — контейнер из четырёх двоеточий `::::`. Шаги идут в верхнем баре в порядке файла.

| Контейнер | Назначение | Обязателен |
|---|---|---|
| `::::warmup` | вопрос до объяснения («что выведет») | нет |
| `::::part Название` | порция объяснения на 3–5 минут, заканчивается 1–2 вопросами | да, хотя бы одна |
| `::::example Название` | разобранный пример | нет |
| `::::practice` | задания по нарастающей | нет |
| `::::traps` | ловушки | нет |
| `::::summary` | итог: ровно один вопрос `recall` | да |
| `::::test` | тест по теме: только вопросы, после `::::summary` | нет |

В `::::summary` поле `answer` вопроса `recall` и есть «Кратко»: оно скрыто, пока пользователь не попробует ответить.

`::::test` не входит в урок. Это **пул** вопросов тех же типов, что в `quickCheck`, без текста и блоков уровня. Каждая попытка берёт из пула `testSize` случайных вопросов (по умолчанию 8), поэтому повторная попытка — другой набор, и тест нельзя пройти по памяти. Вопросы в пуле новые, не повторы из урока: тест проверяет, что тема усвоена, а не что запомнились ответы. Ответы в тесте не показываются до конца, итог — в баллах и процентах; тест пройден от 75 %. Вопросы теста потом попадают в повторение, как и вопросы урока.

В пуле 12–15 вопросов, из них не меньше `testSize` — уровня самой темы. Вопросу теста можно задать `level`: такие вопросы попадают в попытку только читателям этого уровня и выше. Поле `part` с названием шага `::::part` говорит, какую часть урока проверяет вопрос: попытка берёт хотя бы по одному вопросу на каждую часть, пока хватает места. Время в `testMinutes` считают из 40–45 секунд на вопрос.

```yaml
id: test-negative-division
type: output
part: Арифметика               # точное название шага ::::part
prompt: Что выведет код?
...
```

## Блоки уровня

Материал глубже основного уровня темы. Блок уровня — контейнер из трёх двоеточий `:::`, он вкладывается в шаг:

```markdown
:::level middle
Текст, код и вопросы, видимые с уровня Middle.
:::
```

## Вопросы

Вопрос — блок кода с языком `quiz`, внутри YAML. Общие поля:

```yaml
id: boxing-copy          # уникален внутри темы
type: output             # см. таблицу
level: junior            # необязательно, по умолчанию уровень темы
prompt: Что выведет код?
code: |                  # необязательно: код к вопросу, для output, fill и find-bug обязателен
  ...
explain: |               # разбор, показывается после ответа
  ...
```

| type | Что делает пользователь | Специальные поля |
|---|---|---|
| `choice` | выбирает один вариант | `options`, `answer` (индекс с 0) |
| `multi` | выбирает несколько | `options`, `answer` (список индексов) |
| `input` | вводит значение | `answer` (строка или список допустимых), `caseSensitive` |
| `output` | вводит вывод программы | `code`, `answer` |
| `recall` | вспоминает ответ, сам оценивает | `answer` (эталон) |
| `fill` | заполняет пропуск `___` в коде | `code`, `answer` |
| `find-bug` | выбирает строку с ошибкой | `code`, `answer` (номер строки с 1) |
| `parsons` | собирает код из строк | `lines` (в правильном порядке), `distractors` |
| `code` | пишет код, тесты проверяют | `lang`, `starter`, `tests`, `solution` |
| `sql` | пишет запрос | `setup`, `solution`, `ordered` |

Вопрос должен быть понятен без текста статьи: он попадает в повторение, диагностику и тест отдельно от неё. Код, о котором спрашивают, кладётся в `code`, а всё, что нужно знать для ответа и не входит в тему (значения перечисления, сигнатуры чужих методов), — в `prompt`.

### Варианты

Чтобы ответ нельзя было заучить, у вопроса есть варианты: та же проверка на других данных. В `variants` пишутся только поля, которые меняются, остальные берутся из вопроса. `id`, `type`, `level` и `lang` у вариантов общие.

```yaml
id: int-wrap
type: output
prompt: Что выведет код?
code: |
  int x = int.MaxValue;
  Console.WriteLine(x + 1 == int.MinValue);
answer: "True"
explain: |
  ...
variants:
  - code: |
      int x = int.MinValue;
      Console.WriteLine(x - 1 == int.MaxValue);
    explain: |
      ...
```

В первый раз показывается сам вопрос, потом — случайная версия, но не та, что была в прошлый раз. Прогресс у вопроса общий для всех версий. Вариант проверяет то же самое, а не соседнюю мысль: иначе повторение покажет не ту слабость. Если меняется ответ, разбор обычно тоже нужно переписать.

Варианты нужны прежде всего вопросам из `quickCheck` и теста, а также заданиям с кодом: их решают повторно. У `recall` вариантов нет. Каждый вариант задания с кодом сборщик проверяет так же, как основное.

Варианты ответа в `choice` и `multi` перемешиваются при каждом показе. Поэтому варианты не должны ссылаться на своё место: «все перечисленные», «оба первых» не пишут.

Сравнение для `input`, `output`, `fill`: пробелы по краям и переводы строк в конце не важны. Регистр важен, только если `caseSensitive: true`.

### Задания с кодом

`code`: пользовательский код компилируется вместе с `tests`. Тесты — последовательность операторов C#, которые выполняются по порядку внутри сгенерированного метода; доступны `Assert.Equal`, `NotEqual`, `True`, `False`, `Null`, `NotNull` и `Throws<T>`. Пользователю показывается первая проваленная проверка. `solution` — эталон, показывается по кнопке «Показать решение». Сборщик прогоняет `tests` на `solution` так же, как сайт: эталон, который не проходит свои тесты, останавливает сборку. Если тесты проходит уже `starter`, будет предупреждение: такое задание ничего не проверяет. В `starter` тела методов пустые, без `throw new NotImplementedException()` и заглушек вроде `return 0;`: пока метод не написан, сайт покажет ошибку компиляции.

`sql`: `setup` создаёт таблицы и данные в PGlite, `solution` — эталонный запрос. Оба выполняются в транзакции, которая откатывается, так что задания не видят таблиц друг друга. Сравниваются значения последнего оператора, имена столбцов не важны; строки сравниваются как множество, при `ordered: true` — с учётом порядка. Запрос с ошибкой показывается, но не засчитывается как неверный ответ. Эталон SQL сборщик не запускает: PostgreSQL есть только в браузере.
